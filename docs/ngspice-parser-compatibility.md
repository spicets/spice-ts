# ngspice parser compatibility

This matrix audits the TypeScript parser against the ngspice 47+ user manual. It describes syntax acceptance, not numerical model parity. `supported` means the fixture is parsed with its represented semantics; `partial` names the accepted subset; `ignored` is reserved for output-selection metadata that cannot change spice-ts's computed result; `unsupported` means spice-ts rejects the syntax rather than silently discarding it.

Executable fixtures live in [`packages/core/src/parser/ngspice-compatibility.test.ts`](../packages/core/src/parser/ngspice-compatibility.test.ts). Focused lexical regressions live in [`tokenizer.test.ts`](../packages/core/src/parser/tokenizer.test.ts) and [`parser.test.ts`](../packages/core/src/parser/parser.test.ts).

## Counts

| State | Before this audit | After this audit |
| --- | ---: | ---: |
| supported | 13 | 16 |
| partial | 7 | 6 |
| ignored output metadata | 0 | 1 |
| unsupported | 8 | 9 |
| total | 28 | 32 |

The full-row promotions are end-of-line comments, whitespace around `=` in model/instance parameters, and the solver-backed `.options` subset. Independent-source PWL time/value lists are now supported within the still-partial source row. Noise analysis is partial: `v(node) source {lin|dec|oct} points start stop`, ideal-resistor thermal noise at the default 27 C, input/output-referred voltage-noise spectra, and integrated RMS totals are implemented. Numeric scale/unit compatibility remains partial: this audit corrects `mil` to ngspice's `25.4e-6` factor, but does not claim the complete documented numeric grammar. Unsupported semantic directives, unsupported option fields, unsupported resistor parameters, and the unimplemented external source waveform fail explicitly instead of being silently ignored.

Solver-backed fields, the diagnostic-only fields below, and the explicitly diagnosed `bypass` compatibility request are accepted. Values from later `.options` cards replace earlier deck values; explicit API options replace deck values.

## Intentional divergences

### Intentional divergence: degenerate noise output (#1481)

When both `.noise` output terminals resolve to the same node, including
case-folded names and `v(0,0)` (or implicit-ground `v(0)`), spice-ts preserves
the physical zero spectra and integrated totals. It returns one structured
`SimulationWarning` with `type: 'noise'`, `code: 'noise-degenerate-output'`,
`node` set to the positive output name, and a message naming both terminals.
Non-degenerate `v(out)` and `v(out,0)` are unchanged and do not warn.

This intentionally differs from ngspice-47's
[`src/maths/ni/niniter.c`, `NInzIter`](https://sourceforge.net/p/ngspice/ngspice/ci/ngspice-47/tree/src/maths/ni/niniter.c/),
which assigns `rhs[posDrive] = 1` and then `rhs[negDrive] = -1`. When the
indices alias, the second assignment overwrites the first instead of cancelling
it. The resulting nonzero output noise and input noise amplified by the minimum
gain floor are artifacts, not circuit physics. Do not emulate this behavior.
Exclude these degenerate decks from parity scoring as an intentional divergence,
not a parity loss. See [#1481](https://github.com/spicets/spice-ts/issues/1481)
for the identical-input deck and ngspice-47 observations.

## Scope decisions

Option semantics were checked against the [ngspice-47 release source](https://sourceforge.net/p/ngspice/ngspice/ci/ngspice-47/tree/): `src/frontend/spiceif.c` (`noinit`), `src/frontend/inp.c` (`warn`, `maxwarns`, `seedinfo`), `src/spicelib/analysis/cktsopt.c` (`bypass`, `ramptime`), and `src/spicelib/analysis/dctran.c` (ramp-end breakpoint). The V/I source ramp calls in `src/spicelib/devices/{vsrc/vsrcload,isrc/isrcload}.c` are guarded by `XSPICE_EXP`. `src/xspice/cm/cm.c` defines the linear `time/ramptime` factor used by participating code models. This is not the separate cosine ramp used by `optran`. See `benchmarks/options-494` for identical-input receipts and remaining corpus losses.

This compatibility work implements bounded parser and runtime semantics already backed by the native solver: PWL evaluation and the `.options` fields listed above. It does not add device-temperature behavior, measurement evaluation, new analyses, or the remaining source-waveform families; the bounded control-language interpreter is described in the `.control` row above. Those semantic gaps remain explicitly unsupported and keep their executable rejection fixtures.
